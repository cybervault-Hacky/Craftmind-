# CraftMind

**AI Minecraft Builder** · *Describe it. Show it. Build it.*

CraftMind is an Android app for turning a written request into an AI-designed, validated Minecraft build plan. The selected provider/model must return every plan and refinement; CraftMind has no manual block-layout editor, picker, drag-and-drop designer, or built-in structure templates.

## Android AI pipeline · Phase 7 public video references

**Written request and either one image or one supported public video → exact saved provider/model → direct HTTPS image or bounded multi-frame analysis when supported → text-only BuildPlan v2 request to the same model → strict parsing and centralized validation → local review**

**Natural-language refinement → bounded accepted-plan context plus saved text-only image/video notes → exact selected provider/model text + structured-JSON capability checks → strict edit-patch parsing → immutable candidate + domain diff → explicit acceptance → new local version**

The app does not silently change providers, models, capabilities, or schemas. A candidate is kept separate from its saved base until the user accepts it. A provider failure, rejected response, cancellation, or failed local save leaves the previous valid version intact. Retry is user initiated. Restoring an earlier plan appends another local version; it is not Minecraft undo.

## Supported today

- **Provider adapter:** one built-in Google Gemini REST adapter. It lists current models directly from Gemini and supports text generation with JSON MIME output. For visual requests, only the exact live-listed IDs `gemini-3.5-flash` and `gemini-3.5-flash-lite` are marked Vision and Multi-image Vision; those [Gemini 3.5 Flash](https://ai.google.dev/gemini-api/docs/models/gemini-3.5-flash) and [Gemini 3.5 Flash-Lite](https://ai.google.dev/gemini-api/docs/models/gemini-3.5-flash-lite) model cards document image input and structured text output, and Gemini's [image-understanding guide](https://ai.google.dev/gemini-api/docs/generate-content/image-understanding#multiple-images) documents multiple image Parts in one request. Gemini's ListModels response does not advertise input modalities, so the adapter uses this conservative exact-ID capability allowlist in addition to the live `generateContent` listing. Other listed models are text-only in CraftMind even if Google later adds image support. Capability is rechecked at generation; unsupported or stale selections fail with a typed error and are never replaced with a fallback. This allowlist and request path were not verified with a live Google account during this implementation.
- **Provider setup:** enter, replace, remove, and test a Google-owned API key in Settings; select a model only after a live authenticated model-list request succeeds. Model selection labels image-only Vision separately from multi-image/video Vision and text-only models.
- **Credential privacy:** provider keys are AES-GCM encrypted in app-private no-backup storage, with the AES key held by Android Keystore. Keys are not placed in preferences, logs, URLs, analytics, crash reports, build records, a CraftMind backend, or Minecraft. Stored values are never prefilled into the UI.
- **BuildPlan schemas:** new provider-generated plans use semantic BuildPlan v2, including structured intent and typed, bounded components with parent/construction-order relationships. Existing Phase 2 v1 local records remain readable; a successful AI refinement upgrades a legacy plan only when the AI supplies complete valid semantic metadata. The app does not silently repair incomplete plans.
- **Central validation:** strict JSON parsing and shared validation reject unknown/malformed schemas, unsafe block IDs or states, invalid coordinates/dimensions/bounds, broken component relationships, construction-order errors, duplicate/conflicting positions, unsupported operations, missing component placements, and oversized output. Core limits are 96 × 64 × 96 blocks, 64 components, 4,096 placements, a 4 MiB provider response, and 800 characters per refinement request.
- **Bounded refinement context:** context omits image bytes, local URI, and URL values; it includes the accepted plan and, for image/video-assisted builds, only the stored bounded text-only analysis with observed, inferred, and uncertain details kept separate. It includes at most 768 complete placement operations (plus bounded samples when safe), within 96 KiB and the selected model's advertised context limit. Component replacement is rejected unless that component's complete placements were included. Overly broad refinements are refused when safe context cannot be provided. Images and videos are never resent or re-downloaded during refinement.
- **Diff and review:** candidate review identifies provider/model, dimensions, total placement count, semantic components, added/removed/modified components and placements, and suspiciously broad or unrelated changes. Warnings are advisory and are not hidden. A candidate cannot be constructed: it must first be explicitly accepted as a new immutable local version, then separately preflighted and finally confirmed.
- **Local version history:** accepted refinements are stored as immutable versions in atomic app-private local history. Earlier versions are retained; restore creates a new version. No backend or cloud sync is used.
- **Image-to-plan workflow:** one image can accompany a written prompt or be the entire request. JPEG, PNG, and WebP are supported; CraftMind verifies file signatures against the declared MIME type, reads at most 12 MiB, rejects dimensions above 16,384 pixels per side or 80 megapixels, decodes locally, applies supported EXIF orientation, downsamples to at most 4,096 pixels per side and 8 megapixels, strips source metadata by re-encoding, and caps the binary image bytes (before Base64 JSON encoding) at 4 MiB. Prepared payloads are JPEG or PNG; the vision response is capped at 32 KiB and saved text-only evidence at 8 KiB. No raw image bytes are written to history or a CraftMind backend, logged, or sent to analytics/crash reporting. A temporary picker URI and basic reference metadata may be retained in local build history; the raw image is not retained by CraftMind.
- **Direct Gemini routing:** the Android adapter sends validated image bytes directly to `generativelanguage.googleapis.com` using Gemini `inline_data`; there is no CraftMind image server. The first request asks the exact selected Vision model for strict, bounded text analysis. The second request sends only the optional written prompt and that text analysis to the same provider/model for the existing BuildPlan v2; it does not include image bytes. For video, the same adapter sends up to five ordered JPEG frame parts in one bounded multi-image request, then sends only saved text analysis to that same selected model for BuildPlan v2. The exact model ID/provider is rechecked and never changed silently. Provider data retention is governed by Google's terms; CraftMind makes no retention or visual-accuracy guarantee.
- **Observed versus inferred:** image and video analyses return text-only notes that separate observed details, inferred suggestions, and uncertainties. Video frames are treated as stages/views of one source; later clear views are prioritized without assuming the last sample is complete or fabricating unseen geometry. Notes and original provider/model provenance are shown in plan review and saved locally. A video record retains the validated direct URL in app-private history for review, along with source host/type, duration, sample timestamps, model provenance, and bounded text notes—not frame or video bytes. The URL is not included in visual-analysis, BuildPlan-generation, or later refinement provider requests. Existing local records without saved visual analysis are never labeled as analyzed. Refinement reuses saved text notes only; it never resends image/frame data or re-downloads the source.
- **Public video references (narrow allowlist):** only a direct `https://raw.githubusercontent.com/{owner}/{repo}/{branch}/{path}.mp4` or `.webm` file is supported (path requires at least owner/repo/branch/file). No GitHub pages, social/video platforms, other hosts, playlists, manifests, HLS/DASH, `http`, credentials, query strings, fragments, custom ports, IP/localhost/internal destinations, or redirects are accepted. The source must be publicly reachable without login or access-control workarounds and must support HTTP byte ranges. CraftMind probes at most the first 4 KiB, uses direct HTTPS with an exact-host DNS allowlist that rejects any non-public answer, disables proxies and redirects, and revalidates the response URL on every request. Unsupported or inaccessible sources fail with typed errors; URL text, titles, captions, and domains never substitute for visual analysis.
- **Video processing caps:** source file at most 128 MiB; duration 2–180 seconds; source dimensions at most 1,920 × 1,920 and 2,073,600 pixels. Deterministic target samples at 10%, 35%, 60%, 80%, and 95% of duration prioritize a near-end view; at least two distinct frames must decode. At most five frames are kept in RAM, each downscaled to at most 1,024 pixels per side / 1,048,576 pixels and 512 KiB JPEG, with at most 2.5 MiB of frame image bytes in total. Gemini permits at most five parts and caps aggregate raw image payload at 3 MiB. Remote extraction uses 64 KiB byte ranges, at most 128 range requests, a 12 MiB cumulative transfer budget (whichever limit is reached first), five-second connect/read/write timeouts, and a 30-second extraction watchdog. The raw video is never intentionally saved by CraftMind; frame payloads and temporary range buffers are zeroed on completion, failure, or cancellation. Android platform decoding behavior has not been runtime-verified in this checkout.
- **Third-party processing:** video range reads and frame extraction occur on-device, but sampled frame images and the resulting text analysis are sent directly to the selected Google Gemini model for visual analysis; the later BuildPlan request and any refinement text are also sent to that selected provider. Google/provider terms govern processing and retention. CraftMind makes no external retention/privacy guarantee, and no plan claims visual accuracy.
- **Provider network behavior:** provider calls use the built-in HTTPS endpoint directly with bounded response bodies, connection/read/write/call timeouts, cancellation propagation, safe status mapping, disabled redirects, and no automatic retries. The user may explicitly retry retryable failures.

## Phase 10 — multi-version Java compatibility core

CraftMind extends the existing platform-neutral compatibility core rather than replacing its Android, AI, BuildPlan v2, pairing, execution, BYOK, history, website, or release configuration. One central exact-profile registry drives adapter selection and reports typed compatibility status, capabilities, limits, and reason codes. There is no nearest-version fallback, conversion between editions/loaders, silent downgrade, unsafe capability inference, or alternate construction path.

The only production profile remains the genuine baseline: **Java Edition 1.20.1 · Java 17 · Fabric Loader 0.16.10 · Fabric API 0.92.2+1.20.1 · CraftMind Bridge 1.2.0 · protocol 2 · BuildPlan schema 2**. The authenticated capabilities handshake carries and verifies the local CraftMind app version; the bridge reports actual server edition, Minecraft/Java/loader/Fabric API/bridge/protocol versions, bounded limits, world state, and implemented capabilities. Java 17 and Fabric API are checked from those runtime fields, not inferred from the build toolchain or declared dependency. This source profile is configured but is not, by itself, evidence of a successful build, integration, or Minecraft certification.

A pre-existing Bridge 1.1.0 / protocol 1 installation must be upgraded together with the Android app to the matching app plus Bridge 1.2.0 / protocol 2 before use. CraftMind rejects the old protocol with an update-required error, preserves the saved TLS pin, pairing/device identity and server trusted-client record, and never infers the actual JVM or loaded Fabric API. Reconnect after updating both app and existing server mod; no new identity or automatic protocol downgrade is attempted. Other Minecraft versions, Java majors, Legacy, Vanilla, beta/snapshot, and experimental profiles remain unsupported until a concrete adapter is implemented and verified.

BuildPlan v2 remains platform-neutral. Actual capability negotiation uses only the authenticated bridge report; independent live-registry/server validation remains authoritative for each requested block and state. Unsupported content rejects preflight with a stable reason code and, when available, the exact operation index, block ID, and state-property names. CraftMind never substitutes a block or changes an approved plan. Construction still requires `SUPPORTED`, successful server preflight, and separate explicit user confirmation. Settings and Build Review show actual runtime values, status, reported capabilities, limits, and compatibility reasons. See [`docs/universal-minecraft-compatibility.md`](docs/universal-minecraft-compatibility.md) for supported/unsupported profiles, the update policy, and verification boundaries.

## Phase 11 — Bedrock edition compatibility (architecture only, not executable)

CraftMind extends the same compatibility core to Bedrock Edition as a **first-class edition** rather than a second compatibility system: `Platform-neutral AI → BuildPlan v2 → compatibility resolver → {Java adapter → Fabric bridge | Bedrock adapter → Bedrock bridge} → Minecraft world`.

- **Editions stay disjoint.** Bedrock is represented exclusively as `MinecraftLoader.BEDROCK_NATIVE`; Bedrock runtimes never carry `FABRIC`/`FORGE`/`NEOFORGE`/`VANILLA` labels and never report a JVM, loader version, or Fabric API version. Java runtimes never report a Bedrock platform. A mismatch fails closed as an invalid descriptor.
- **Bedrock versions are independent of Java versions.** `Java 1.20.1` and `Bedrock 1.20.1` are unrelated identifiers: there is no cross-edition matching, normalization, nearest-version fallback, or inference from a launcher name, user selection, filename, or heuristic. Bedrock runtime detection is authoritative from the authenticated bridge report only.
- **One deliberate Bedrock contract, uncertified.** `BedrockRuntimeProfileRegistry` ships exactly one `bedrock-bridge-contract` (CraftMind Bedrock bridge interface version `1.0.0`, protocol `2`) with **no certified Bedrock version**, certification `NOT_PERFORMED`, an **empty block/state catalog**, and status `EXPERIMENTAL`. A matching Bedrock runtime therefore resolves to `EXPERIMENTAL`, never `SUPPORTED`; the adapter's preflight/execute/cancel/status members throw a typed failure instead of forwarding a BuildPlan, and the empty catalog makes every requested block unsupported. Real Bedrock support requires a recorded runtime verification before any version is registered.
- **Bridge boundary.** The Bedrock integration mechanism is a **Bedrock Dedicated Server + CraftMind Bedrock bridge** (or another documented, supported mechanism) speaking the existing authenticated protocol-v2 envelope. Bedrock worlds cannot load the Java Fabric mod; no shim, screen scraping, input simulation, injection, patching, or anti-cheat/DRM/license bypass exists anywhere in this project.
- **Shared, not duplicated.** Protocol concepts, authentication/session handling, BuildPlan validation, capability negotiation, execution IDs, status, cancellation, limits, the error model, and the Android pairing flow are shared with the Java path. Capability negotiation uses only bridge-reported values with explicit, non-automatic grants; a capability outside the declared Bedrock contract makes the result `UNKNOWN`.
- **BuildPlan v2 stays platform-neutral.** The AI never silently changes a plan for Bedrock, and app-side resolution is never the authority: the Bedrock bridge must independently validate schema, size, dimensions, operation count, block/state validity, coordinate bounds, execution ID, protocol version, capability requirements, runtime compatibility, and auth/session validity against the shared `BuildPlanLimits`.
- **Honest UI and diagnostics.** Settings and Build Review show edition, Minecraft and Bedrock platform version, bridge/protocol, status, certification level, capabilities, missing capabilities, declared limitations, and limit/content checks. A non-supported Bedrock runtime shows *"not currently supported … No BuildPlan will be sent for execution."*, final confirmation stays disabled, no fabricated progress or premature `completed` is possible, and restart recovery reports `FAILED`/`RECOVERY_REQUIRED` instead of auto-resuming.
- **Bedrock status in this build:** **architecture EXPERIMENTAL, execution UNSUPPORTED.** No Bedrock bridge implementation, no Bedrock runtime test, and no node is certified here; no Bedrock version is claimed to work.

## Phase 12 — legacy, beta, and experimental compatibility (recognized, never executable)

CraftMind now models older Java releases, historical loader/runtime combinations, beta/pre-release/snapshot identifiers, and experimental protocols **in the same compatibility core** — same resolver, adapter registry, version model, capability negotiation, limits, diagnostics, and execution gate. The rule enforced everywhere is simple: *recognizing an old, beta, snapshot, or experimental Minecraft runtime is not the same as supporting it.*

- **Explicit legacy classification, never automatic.** `MinecraftVersion.parse("1.7.10")` stays `RELEASE`; a target is legacy only because a registered profile says so (`SupportedMinecraftRuntimeDescriptor.releaseChannel = LEGACY`). The registry rejects a declared channel the identifier cannot carry.
- **Two declared contracts, uncertified and non-executable.** `LegacyRuntimeProfileRegistry` ships `java-legacy-forge-1.7.10` (Forge `10.13.4.1614`) and `java-legacy-forge-1.12.2` (Forge `14.23.5.2859`), each with **Java 8 exactly**, status `EXPERIMENTAL`, certification `NOT_PERFORMED`, an explicit limitation set (no rollback, no automatic resume, progress only bridge-reported, block/state mapping unverified, …), an empty unverified app-side block/state catalog, and a declared legacy bridge *interface contract* `1.0.0-legacy` (a boundary definition, not a deployed bridge). A recognized legacy runtime resolves to `EXPERIMENTAL`/`RUNTIME_NOT_CERTIFIED`; `preflight`/`execute`/`cancel`/`status` throw a typed failure **before any bridge call**, so no BuildPlan is forwarded.
- **Release channels are typed and diagnosed.** `RELEASE`/`PRE_RELEASE`/`SNAPSHOT`/`BETA`/`ALPHA`/`LEGACY`/`UNKNOWN`. An unregistered snapshot/beta/alpha/pre-release runtime fails closed with `UNSUPPORTED_RELEASE_CHANNEL`; a classic/beta-era identifier fails with `UNSUPPORTED_LEGACY_VERSION`; an unregistered release fails with `UNSUPPORTED_MINECRAFT_VERSION`. All three state that the runtime is never matched to a release build: no nearest-version fallback, no cross-edition matching, no naive string comparison.
- **Version model.** Structured `major`/`minor`/`patch`, pre-release qualifier, parsed channel, and the exact bounded identifier. Malformed or unsafe tokens become `UNKNOWN` and are never assumed to be a nearby release.
- **Java runtime requirements stay per-release.** The legacy contracts require Java 8; a bridge reporting Java 17 (or 7) gets `INCOMPATIBLE_JAVA_RUNTIME` instead of an assumption that "Java 17 probably works".
- **Loaders stay explicit.** Fabric, Forge, NeoForge, Vanilla, Bedrock Native and Unknown are matched on exact identity only. Forge/NeoForge/Vanilla never borrow the Fabric 1.20.1 adapter, an old vanilla runtime is never mapped to the Forge contract, and a legacy Forge runtime reporting Fabric is `UNSUPPORTED_LOADER`.
- **Certification ladder, never collapsed.** `NOT_PERFORMED` → `STATIC_ONLY` → `UNIT_TESTED` → `BRIDGE_TESTED` → `RUNTIME_TESTED` → `CERTIFIED`. Only `RUNTIME_TESTED`/`CERTIFIED` may back `SUPPORTED`; Bedrock still requires `RUNTIME_TESTED`. The registry rejects an over-claimed profile, and the adapter re-checks so an uncertified runtime can never surface as `SUPPORTED`.
- **Block/state fail-closed.** One generic `MinecraftTargetBlockStateCatalog` maps platform-neutral blocks/state values to a declared target representation. Unverified mappings are rejected at construction, and unmapped blocks/states produce `UNSUPPORTED_BLOCK`/`UNSUPPORTED_BLOCK_STATE`. CraftMind never substitutes a block, a state value, a loader, or a Minecraft version.
- **BuildPlan v2 stays platform-neutral.** No legacy/beta-specific plans. The shared limits and schema checks still apply (`UNSUPPORTED_BUILDPLAN_SCHEMA`, `PLAN_LIMIT_EXCEEDED`); runtime-reported limits are combined with the profile by taking the stricter value, missing limits fail closed, and limits are never loosened for legacy targets.
- **UI.** Settings and Build Review show edition, Minecraft version, **release channel**, Java/loader (or Bedrock platform), bridge/protocol, recorded certification, declared limitations, capabilities/gaps, structured reasons and effective limits. The honest summary (status, channel, certification, limitations, "Build unavailable … No BuildPlan will be sent for execution") is always visible; raw capability/adapter detail is collapsible, and construction stays disabled unless the runtime resolves to `SUPPORTED` and every capability, content, limit, and preflight check passes.
- **Status in this build:** **architecture implemented; legacy/beta/experimental execution UNSUPPORTED.** No legacy bridge, no legacy runtime test, and no legacy certification exists here; the declared contracts exist so the app can *recognize* those runtimes and refuse them honestly. Security (pairing, transport, replay protection, bounded parsing, execution IDs, capability and server-side BuildPlan validation, cancellation, single-active-build, typed errors) applies unchanged — legacy code is never an exception.

## Phase 13 — automatic runtime detection and deterministic adapter selection

CraftMind no longer treats the Minecraft runtime as something the app already knows. The authenticated bridge reports
it, CraftMind **detects** it, validates it, selects exactly one compatibility adapter for it, resolves compatibility,
and binds the whole answer to that authenticated session. Detection adds no second runtime model, registry, resolver,
or block/state layer: it extends the existing descriptor and reuses the existing registry, adapters, and resolver.

- **One ordered pipeline.** `authenticated bridge → runtime descriptor → detection → descriptor validation → adapter selection → compatibility resolution → session-bound eligibility → final pre-execution authorization`, implemented as `MinecraftRuntimeDetector` → `MinecraftRuntimeDescriptorValidation` → `MinecraftAdapterSelector` → `MinecraftCompatibilityResolver` → `MinecraftRuntimeCompatibilityGate`.
- **Detection is typed and deterministic.** `MinecraftRuntimeDetectionResult` carries `DETECTED / INCOMPLETE / UNKNOWN / INVALID`, the authoritative descriptor, the bound `MinecraftRuntimeIdentity`, and bounded diagnostics with structured reason codes. The same authenticated report always produces the same result; nothing is guessed and nothing is silently corrected.
- **Only an authenticated report can be detected.** `AuthenticatedMinecraftRuntimeReport` is the sole detection input, so an unauthenticated caller is refused with `RUNTIME_DETECTION_UNAUTHORIZED` before any field is read. Launcher names, executables, APK settings, package names, filenames, ports, typed versions, UI selections, previous connections, and saved preferences are never runtime sources.
- **Edition, version, channel, loader, Java runtime.** `JAVA`/`BEDROCK`/`LEGACY`/`UNKNOWN` editions with strict edition↔loader coherence (`JAVA`+Fabric/Forge/NeoForge/Vanilla, `BEDROCK`+`BEDROCK_NATIVE`; anything else is `INVALID_RUNTIME_DESCRIPTOR`). A legacy Java runtime is `JAVA` + the `LEGACY` release channel, never a third edition. Versions are exact (`1.20.1`, `1.19.4`, `1.12.2`, `1.7.10`, snapshots, betas, alphas, pre-releases, legacy tokens, or unknown) with **no nearest-version fallback**. The release channel is derived from the authoritative identifier, and a registered profile's explicit declaration may reclassify an exact identity as legacy — a contradictory declaration invalidates the descriptor instead of being corrected. Java runtime majors are validated per profile (`1.20.1`→Java 17, `1.7.10`/`1.12.2` Forge→Java 8); a mismatch is `INCOMPATIBLE_JAVA_RUNTIME` and blocks execution.
- **Bridge, protocol, app version, capabilities, limits.** `bridgeProtocolVersion` must be exactly protocol 2 and `bridgeVersion` must be declared by a registered profile/contract, so a correct Minecraft version with an incompatible bridge still fails (no downgrade). The app-version echo is re-verified at detection (`APP_VERSION_MISMATCH`, fail closed). Capabilities come only from the authenticated report; a report whose capabilities contradict its own facts, or that claims a capability this build does not define, is rejected as forged. Claiming `BUILD_EXECUTION` never makes an uncertified runtime executable. Effective limits stay `min(CraftMind global limit, runtime-reported limit)`, and a missing required limit keeps detection `INCOMPLETE` and execution blocked.
- **Deterministic adapter selection.** `CompatibilityAdapterSelection` returns `SELECTED / NO_MATCH / AMBIGUOUS / INVALID` with the matched profile or Bedrock contract and the full candidate list ordered by adapter ID. Exact matching only: no nearest adapter, no cross-edition matching, and two adapters claiming one runtime produce `AMBIGUOUS_ADAPTER_MATCH` instead of a registration-order choice. Selection runs only after pairing, authentication, protocol, descriptor, app-version, and capability validation, and **selection never implies executability**.
- **Session binding, reconnection, runtime change, TOCTOU.** Compatibility is bound to `MinecraftRuntimeIdentity` (bridge ID, pinned TLS fingerprint, session ID, authentication time, and the exact runtime key). Reconnecting or refreshing capabilities re-runs the whole pipeline; a cached descriptor is historical information only. A changed runtime (`1.20.1 → 1.19.4`), loader, bridge, adapter, session, or world invalidates prior eligibility (`RUNTIME_IDENTITY_CHANGED`, `SESSION_IDENTITY_MISMATCH`, `WORLD_SESSION_CHANGED`), and `authorizeExecution` re-checks everything immediately before a BuildPlan is sent, so the runtime at preflight must be the runtime that was resolved.
- **No manual override.** There is no UI to choose an edition, Minecraft version, loader, or adapter, and no "execute anyway" control. The only runtime-related preference is a display toggle for technical detail.
- **UI.** Minecraft Settings gains a **Minecraft Runtime** section (detected edition, version, release channel, loader/Fabric API or Bedrock platform, Java runtime, bridge/protocol, compatibility, certification, selected adapter and selection status, pipeline phase, limitations, structured reasons, session/runtime binding). Build Review shows **"Target Runtime: Detected automatically"**, and an unavailable build shows `Build unavailable` with "No BuildPlan will be sent for execution" while the final confirmation stays disabled.
- **No protocol change.** Detection uses only fields protocol 2 already mandates and the codecs already bound/validate, so `BridgeProtocol.VERSION` stays 2 and the Fabric bridge sources are unchanged.
- **Preserved behaviour.** Bedrock remains `EXPERIMENTAL` + `NOT_PERFORMED` with no certified version and no execution path; legacy runtimes remain exactly recognized, `EXPERIMENTAL`, `RUNTIME_NOT_CERTIFIED`, and non-executable with typed refusals before any bridge call; the production Java profile (`1.20.1`, Java 17, Fabric Loader `0.16.10`, Fabric API `0.92.2+1.20.1`, Bridge `1.2.0`, protocol 2, BuildPlan schema 2) is unchanged; every Phase 1–12 security control still applies.

## Phase 14 — universal end-to-end testing and certification

Phase 14 makes certification evidence explicit, reproducible, and impossible to claim without evidence. It adds one
certification model, one evidence record, one decision engine, one universal test matrix, a simulated end-to-end
pipeline, a real-runtime certification hook, a deterministic certification BuildPlan, a machine-readable report, and
honest status wording. Full detail: [`docs/minecraft-certification-testing.md`](docs/minecraft-certification-testing.md).

- **Seven verification layers, never conflated.** `STATIC`, `UNIT`, `PROTOCOL`, `SIMULATED_INTEGRATION`, `REAL_RUNTIME_INTEGRATION`, `END_TO_END_EXECUTION`, `CERTIFICATION_DECISION`, each with an explicit outcome (`PASSED`/`FAILED`/`NOT_RUN`/`NOT_AVAILABLE`/`NOT_PERFORMED`/`BLOCKED`). A skipped check is never a pass.
- **One evidence ladder.** `NOT_PERFORMED → STATIC_ONLY → UNIT_TESTED → BRIDGE_TESTED → SIMULATED_E2E_VERIFIED → RUNTIME_TESTED → CERTIFIED`, ordered by explicit `evidenceRank`. Phase 14 added exactly one rung, `SIMULATED_E2E_VERIFIED`: a full pipeline run against a controlled simulated bridge is real evidence about CraftMind's wiring, is capped by `MAXIMUM_SIMULATED_LEVEL`, never authorizes support, and can never be upgraded to a runtime rung.
- **Structured evidence, sanitized.** `MinecraftCertificationEvidence` records profile, edition, version, channel, loader, Java runtime, Fabric API, bridge and protocol version, BuildPlan schema, catalog revision, suite/run IDs, environment, timestamp only when a run happened, level, mode, per-category outcomes, execution evidence, limitations, decision inputs, and whether a real runtime test occurred. `MinecraftCertificationSanitizer` **rejects** (never redacts) private keys, credential assignments, bearer/vendor tokens, IPv4 addresses, host names, keystore/`.pem` paths, and TLS fingerprints.
- **One decision engine.** `MinecraftCertificationRuleEngine` returns `CERTIFIED | NOT_CERTIFIED | INSUFFICIENT_EVIDENCE | BLOCKED_BY_LIMITATION | FAILED` deterministically. Nothing certifies because an adapter exists, a resolver matched, a unit test passed, a fake bridge responded, a BuildPlan validated, a capability report parsed, or a runtime is theoretically compatible. `MinecraftCertificationPolicy.DEFAULT.realRuntimeCapableEnvironments` is **empty**, so no environment in this repository can mint new certification.
- **Shipped record kept separate from new evidence.** Java 1.20.1 stays `SUPPORTED`/`CERTIFIED` as CraftMind's shipped production target and is **not** downgraded because this sandbox has no Minecraft; `evaluateShippedRecord` reports it with `evidenceMode = NONE`, `source = SHIPPED_PRODUCTION_RECORD`, and a policy statement recording that Phase 14 performed no new real-runtime test and adds no new runtime evidence. Bedrock and legacy contracts stay `EXPERIMENTAL` / `NOT_PERFORMED` / `NOT_CERTIFIED` with execution disabled.
- **Universal matrix, executed.** 35 runtime rows (Java production, Forge 1.7.10 and 1.12.2, the Bedrock contract, 19 unsupported/invalid cases, 11 security cases) plus 15 execution failure cases, each declaring which layers apply. `CertificationMatrixTest` drives every row through production code and asserts detection status, selection status, stable reason code, adapter, executability, and certification decision.
- **Simulated end-to-end pipeline.** `SimulatedCertificationPipeline` runs authentication → capability exchange → app-version echo → detection → descriptor validation → adapter selection → compatibility resolution → BuildPlan validation → preflight → execution authorization → execution → progress → cancellation → completion through production code against a protocol-faithful fake bridge, without bypassing a layer. It proves wiring only: level `SIMULATED_E2E_VERIFIED`, mode `SIMULATED`, decision `NOT_CERTIFIED`.
- **Execution depth is distinguished.** `REQUEST_ACCEPTED`, `PRECHECK_PASSED`, `EXECUTION_STARTED`, `BLOCKS_WRITTEN`, `PROGRESS_REPORTED`, `EXECUTION_COMPLETED`, `EXECUTION_CANCELLED`, `EXECUTION_FAILED`; the three world-touching stages are marked `requiresRealWorld`, so simulation can never claim them and a cancelled run writes at most a bounded prefix.
- **Failure injection fails closed.** 15 documented cases (authentication, invalid session, session/runtime identity change, bridge identity mismatch, app-version mismatch, protocol mismatch, unsupported version/loader, Fabric API mismatch, malformed descriptor, forged capability, missing limits, invalid BuildPlan, unsupported block/state, preflight rejection, duplicate execution ID, second simultaneous build, cancellation, disconnect, reconnect, stale binding, adapter ambiguity) each assert the documented reason code, the refusing stage, and that nothing was written before the validation that refused it.
- **Security regression at the certification layer.** Pinned HTTPS pairing (static source verification), mandatory authentication, replay/staleness refusal, session binding, authenticated runtime identity, bridge-reported capabilities only, forged-capability refusal, protocol and schema downgrade refusal, `min(global, runtime)` limits that a client can never raise, server-side block/state validation, no command/shell/credential surface, and no secret, host, session, or fingerprint in evidence, reports, or committed artifacts.
- **Real-runtime hook, honestly idle.** `MinecraftRealRuntimeCertificationHarness` performs 17 steps against a `MinecraftRealRuntimeHost`; the shipped `NoRealRuntimeHostProvider` supplies none, so every step is `NOT_PERFORMED`, the outcome is `RUNTIME_TEST_NOT_PERFORMED`, and nothing is certified. No Minecraft download, no network access, and no fake server is ever called real. A host that claims to be real still cannot certify unless the policy declares its environment.
- **Deterministic certification BuildPlan.** A three-placement probe inside 3×1×3 bounds, `PLACE_BLOCK` only, schema 2, validated by the same `DefaultBuildPlanValidator`, `MinecraftBlockCatalog`, and bridge contract validator as a user build. Production validation was not weakened: the suite asserts the probe passes *and* that the validator still rejects unsupported blocks, invalid states, empty operations, invalid/duplicate coordinates, unsupported schemas, and oversized operation lists.

### Phase 5: controlled construction workflow

Construction remains an opt-in extension of the existing paired bridge, not a second connection service. The operator must deliberately set `constructionEnabled=true` in `config/craftmind-bridge.properties`; the generated default is `false`. The Phase 10 resolver additionally requires an exact registered runtime profile, bridge-reported capabilities, BuildPlan schema 2, usable operation/request/batch/time limits, world access, cancellation, and a current operator-selected origin. Phase 13 adds the detection precondition: the runtime must have been detected from the authenticated session, exactly one adapter must have been selected for it, and the resulting eligibility must still be bound to the same session and runtime immediately before execution (re-checked at preflight and again at start). Pairing alone never enables construction; otherwise every construction action remains disabled.

1. **Pair using the existing flow.** The operator uses `/craftmind identity`, `/craftmind pair open`, and Android Settings to verify the bridge ID and TLS fingerprint and pair the device. Pairing is explicit; an operator can list/revoke devices. Provider API keys remain on Android and are never included in bridge requests.
2. **Select a safe origin in game.** An operator runs `/craftmind origin set` while standing at the intended anchor. The bridge captures that player's block position and the current dimension; no coordinates can be entered in the app or sent as an arbitrary placement origin. `/craftmind origin status` shows it and `/craftmind origin clear` removes it. The selected origin is memory-only and tied to a fresh world-session ID, so a server restart clears it. Moving or changing the selected origin invalidates prepared/active work before another placement.
3. **Choose an accepted immutable plan version.** Only the latest, locally saved, validated BuildPlan v2 in `READY` state can be prepared. A candidate refinement must be explicitly accepted first. The client sends the exact saved plan/version to the typed prepare route; it cannot edit or choose blocks/coordinates for execution.
4. **Run server preflight.** On the Minecraft server thread, the bridge checks the trusted authenticated client, protocol and schema, UUID execution ID and idempotency binding, operation/request limits, plan/component/semantic order, supported origin/dimension/world session, registered vanilla block IDs and state properties, transforms, loaded chunks, world height/border, unoccupied target cells, non-spectator entity collisions, vanilla spawn protection, and each block state's `canPlaceAt` against the existing world plus earlier operations in plan order. No blocks are placed during preflight. Any failed check rejects the whole preflight with zero writes; chunks are not force-loaded and invalid blocks/states are not skipped or repaired.
5. **Review a resolved preview, then confirm again.** Android displays the server-resolved world, dimension, operator-selected origin, immutable plan title/version, operation count, and preflight expiry. A separate confirmation dialog repeats the summary and warns that failure/cancellation can leave partial world changes. Only a fresh, authenticated final confirmation with the short-lived server token may start placement; start re-runs preflight before queueing.
6. **Observe actual server status.** The single active execution is placed in semantic BuildPlan operation order from bounded END_SERVER_TICK batches. The default is 32 attempted placements per tick, configurable up to 64. The default execution timeout is five minutes, configurable up to 15 minutes. Before each placement, the bridge rechecks the current origin, world bounds, border, loaded chunk, occupancy, entities, block state, and placement support, then uses Minecraft's `ServerWorld.setBlockState` and confirms the target block still occupies that cell; progress is stored only after both checks succeed. Android polls the authenticated status route and shows bridge snapshots; it never estimates progress locally. Cancellation is a best-effort request applied at the next safe tick boundary; the currently executing bounded batch (at most 64 placements) can finish first.
7. **Reconnect and restart safely.** Execution IDs are bound to the trusted client and payload hash; same-ID prepare/start retries are idempotent, conflicting reuse is rejected, and the server permits only one prepared/queued/running build at a time. Android stores execution snapshots in a separate bounded local ledger; it never mutates immutable plan records. On reconnect, Android queries the bridge's saved record; it never auto-starts a `PREPARED` execution. The mod marks prepared/queued/running records `FAILED` with `SERVER_RESTARTED` at shutdown/startup and never resumes. If the process crashes between a world write and its status-file checkpoint—or before Minecraft saves the affected chunk—the last persisted count may differ from the recovered world. The app warns operators to inspect the world in game; CraftMind has no automatic reconciliation, duplicate prevention across a **new** manual execution, rollback, or undo for partially placed blocks. Do not blindly retry an interrupted plan.

### Execution limits and supported world policy

The generated server defaults are `maxOperations=4096`, `maxRequestBytes=1048576` (1 MiB), `operationsPerTick=32`, and `maxExecutionSeconds=300`. The hard ceilings are 4,096 operations, 1 MiB, 64 operations/tick, and 900 seconds; out-of-range config is rejected at startup. A bridge allows one active or prepared execution, preflight tokens expire after 120 seconds, and both the server-side and Android-local execution ledgers are separately bounded to 100 records/256 KiB; neither replaces immutable plan history. Plan dimensions remain capped at 96 × 64 × 96, 64 semantic components, and 4,096 placements. Coordinates are transformed with checked arithmetic; transformed X/Z are bounded to ±30,000,000 and transformed Y to `-2048..2048`, then checked again against the loaded world's actual height and border.

Only the exact registered stack below is supported: Minecraft `1.20.1`, Java `17`, Fabric Loader `0.16.10`, Fabric API `0.92.2+1.20.1`, CraftMind Bridge `1.2.0`, protocol `2`, and BuildPlan schema `2`. The authenticated protocol-v2 report includes actual Java, Fabric API, and capability values. Existing Bridge `1.1.0` / protocol `1` installations must upgrade; saved pairing identity is retained, but no runtime values are inferred and no protocol downgrade is attempted. In addition to the four base mod IDs `minecraft`, `fabricloader`, `fabric-api`, and `craftmind_bridge`, the mod policy permits only the module IDs bundled by the pinned Fabric API `0.92.2+1.20.1`: `fabric-api-base`, `fabric-api-lookup-api-v1`, `fabric-biome-api-v1`, `fabric-block-api-v1`, `fabric-block-view-api-v2`, `fabric-blockrenderlayer-v1`, `fabric-client-tags-api-v1`, `fabric-command-api-v1`, `fabric-command-api-v2`, `fabric-commands-v0`, `fabric-containers-v0`, `fabric-content-registries-v0`, `fabric-convention-tags-v1`, `fabric-crash-report-info-v1`, `fabric-data-attachment-api-v1`, `fabric-data-generation-api-v1`, `fabric-dimensions-v1`, `fabric-entity-events-v1`, `fabric-events-interaction-v0`, `fabric-events-lifecycle-v0`, `fabric-game-rule-api-v1`, `fabric-item-api-v1`, `fabric-item-group-api-v1`, `fabric-key-binding-api-v1`, `fabric-keybindings-v0`, `fabric-lifecycle-events-v1`, `fabric-loot-api-v2`, `fabric-loot-tables-v1`, `fabric-message-api-v1`, `fabric-mining-level-api-v1`, `fabric-model-loading-api-v1`, `fabric-models-v0`, `fabric-networking-api-v1`, `fabric-networking-v0`, `fabric-object-builder-api-v1`, `fabric-particles-v1`, `fabric-recipe-api-v1`, `fabric-registry-sync-v0`, `fabric-renderer-api-v1`, `fabric-renderer-indigo`, `fabric-renderer-registries-v1`, `fabric-rendering-data-attachment-v1`, `fabric-rendering-fluids-v1`, `fabric-rendering-v0`, `fabric-rendering-v1`, `fabric-resource-conditions-api-v1`, `fabric-resource-loader-v0`, `fabric-screen-api-v1`, `fabric-screen-handler-api-v1`, `fabric-sound-api-v1`, `fabric-transfer-api-v1`, and `fabric-transitive-access-wideners-v1`. ### What the bridge implements

- **Typed protocol-v2 contracts:** bounded strict JSON envelopes, UUID request/correlation IDs, version checks, typed errors, rate/body/depth/operation limits, BuildPlan v2 transport DTOs, and independent validation of IDs, dimensions, coordinates, components, operation count, vanilla block IDs, and registered block-state properties.
- **Typed execution semantics:** the bridge has separate prepare, start, status, and cancel routes. Prepare validates the complete request and server world without writing any blocks. Only a short-lived server-issued token plus a later authenticated start request can queue execution. Status, progress counts, terminal state, cancellation, and errors come from the bridge coordinator; unknown or mismatched IDs never imply success.
- **Encrypted, pinned transport:** HTTPS only (TLS 1.2/1.3), a server certificate whose private key is stored in password-protected PKCS#12, and Android verification against the SHA-256 certificate fingerprint entered out-of-band from the in-game identity command. Android accepts only strict loopback/RFC1918 IPv4 literals—no DNS, public address, IPv6, redirects, or cleartext fallback. The server binds to one loopback/RFC1918 IPv4 address and accepts remote peers only from loopback, RFC1918, or IPv4 link-local ranges.
- **Explicit device pairing:** an operator opens a one-use, 256-bit pairing code for three minutes. The Android app proves possession of a P-256 key generated and held by Android Keystore. The server persists only the Android public key and display metadata in a bounded, atomically replaced trusted-client file; pairing codes, challenges, and sessions are memory-only.
- **Authenticated sessions and revocation:** expiring one-time challenges, P-256 signed proof-of-possession, request signatures over exact body bytes, route, method, request ID, timestamp, session ID, and monotonically increasing sequence; replayed/stale requests are rejected. Sessions expire after five minutes idle and at 30 minutes maximum age. The app can reconnect by authenticating again, explicitly disconnect a session, remotely revoke its paired key, or forget local state. Operator revocation removes the trusted record and invalidates sessions/challenges.
- **No arbitrary control surface:** only an exact authenticated POST route allowlist is exposed. There is no shell, arbitrary command execution, screen/mouse/keyboard automation, fake player, simulated input, remote console, or general-purpose LAN API. The only mutation path is the typed BuildPlan-v2 execution lifecycle, which uses the server's world APIs and independently validates every requested block/state.

### Pairing and server setup

1. Install the server-only Fabric mod built from `minecraft-bridge/` on the configured compatibility matrix and only the supported Fabric API module set above. Any extra/unknown mod disables construction. It creates `config/craftmind-bridge.properties`; the default listener is loopback-only (`127.0.0.1:19872`) and `constructionEnabled` defaults to `false`.
2. For a phone on a private LAN, set `bindAddress` to the server's private IPv4 address and allow the configured port through the local firewall. Do not port-forward or expose the listener to the public Internet. Configure the address **before first startup with the keystore password set**, so the durable TLS certificate is minted with the right IP Subject Alternative Name.
3. Set `CRAFTMIND_BRIDGE_KEYSTORE_PASSWORD` in the server process environment to a strong password of at least 16 characters. It is never written to the properties file. Without it the bridge listener stays disabled; core app functions and local plan history remain available without Minecraft connectivity. To explicitly permit construction, review the safety limits and set `constructionEnabled=true` in the properties file; do not enable it on an unsupported/modded server. The encrypted identity, trusted-client, and separate bounded execution-record files are under `config/craftmind-bridge/`.
4. In game, an operator runs `/craftmind identity` and checks the public bridge ID/TLS SHA-256 fingerprint. Then `/craftmind pair open` shows the one-time code privately to that in-game operator; it expires after three minutes. Enter the private IPv4, port, fingerprint, and code in **Settings → Minecraft bridge** on Android. 5. Android persists only the confirmed endpoint/pin/client metadata in app-private DataStore and keeps the private client key in Android Keystore. ### Deliberate limitations

- Only one saved bridge profile and a manually entered private IPv4 endpoint are supported; discovery, DNS names, QR pairing, IPv6, internet-facing servers, and automatic identity replacement are not.
- Changing the server bind IP after creating its certificate fails closed with `IDENTITY_ADDRESS_CHANGED_REQUIRES_REPAIR`. The operator must deliberately back up/remove the identity file and generate a new one; this changes the TLS fingerprint and bridge ID. Previously paired clients must be reviewed/revoked; Android requires explicit re-pairing against the new fingerprint.
- No rollback, undo, automatic continuation, or automatic reconciliation of uncertain world state is implemented. A graceful cancellation/failure may leave partial changes. A server restart records `FAILED / SERVER_RESTARTED` and never resumes; the last persisted count may not exactly match the recovered world if a crash races a world write or chunk save. Inspect the world in game before starting another build.
- Claim/region-protection mods, custom permissions, other modded block registries, block-entity data, gravity-sensitive blocks, arbitrary coordinates, structure replacement, and remote commands are unsupported. Any extra mod fails construction closed; no special protection integration or permission bypass is provided.
- The bridge foundation has not undergone an independent security audit. Configuration and tests are not a substitute for an audit or safe private-network deployment.

### Release workflow

Create the external keystore and load its values into a local shell or CI secret store, then run `./gradlew :app:assembleRelease`. Inspect a produced APK with `scripts/verify-release-apk.sh`; it checks the application ID/version, invokes `apksigner` verification, prints the public signer-certificate SHA-256 fingerprint, and calculates the APK SHA-256. Compare the certificate fingerprint with a previously recorded trusted value; the helper does not establish runtime compatibility or replace device/provider/Minecraft tests. Publish only a verified signed APK and matching checksum. The `1.0.0` release versionCode is `10000`; future releases must increase it. See [`RELEASE_CHECKLIST.md`](RELEASE_CHECKLIST.md) before making a public release.

The website's disabled APK button must be changed only after the exact signed release asset exists. Then rerun `python3 scripts/check_website.py`. To use GitHub Pages, configure Pages for GitHub Actions and, from a GitHub connection permitted to manage workflow files, copy `website/github-pages-workflow.yml.example` to `.github/workflows/publish-website.yml` and trigger it manually. No deployment is active in this branch. No Play Store release, AAB-only distribution, monetization, ads, hosted account service, or AI gateway is part of this release scope; account-service source exists in `backend/` but is not deployed.
