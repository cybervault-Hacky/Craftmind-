THE SIX-STEP FLOW

From a sentence
to a placed block.

CraftMind is AI-first and review-first. Every stage below exists in the app today, and every stage can stop with a plain-language reason instead of pretending to continue.

IMPLEMENTED BEHAVIOUR

Six steps, in order.

No step is simulated. When something cannot run — no provider key, an unusable reference, an unsupported runtime — the app explains why instead of showing invented progress.

  1. STEP 01

    Describe the build

    A text prompt is required. CraftMind sends it straight from the device to the AI provider you configured, using the credential you saved. Nothing is forwarded to a CraftMind server, because there is none.

  2. STEP 02

    Add one visual reference (optional)

    A locally checked JPEG, PNG, or WebP image, or one narrowly supported public MP4/WebM file URL on raw.githubusercontent.com. Images are validated and bounded on the device; video bytes are fetched in bounded ranges and only sampled frames are sent as extra vision input.

  3. STEP 03

    The model drafts a BuildPlan

    The provider must return the CraftMind BuildPlan v2 structured document. Free-form prose, partial documents, or anything outside the schema is rejected as an invalid provider response.

  4. STEP 04

    CraftMind validates the plan

    Bounded parsing checks structure, dimensions, floors, components, materials, and operation counts. Only a validated plan becomes a reviewable build; a rejected plan never enters your history as a build.

  5. STEP 05

    You review, refine, and save

    The review screen shows title, summary, dimensions, components, materials, floors and sections, compatibility, the source reference, warnings, and validation status — with technical detail collapsed until you ask for it. Refinement sends a new provider request and saves the result as a new version.

  6. STEP 06

    Build only if you choose

    Pairing an optional Fabric bridge is a separate decision. The bridge must authenticate, the runtime is detected from its authenticated report, exactly one adapter must match, compatibility and limits are resolved, and the server preflights the plan before a final confirmation. Progress you see comes from the bridge, never from an animation.

Why building stays unavailable

Execution is gated four times, in this order. Each gate is implemented in the app and in the bridge, and a failed gate stops the flow with a reason instead of a disabled button.

  • Detection — the Minecraft runtime is read only from the authenticated bridge report. Nothing is guessed or defaulted.
  • Adapter selection — exactly one registered adapter must match the detected runtime; an ambiguous match fails closed.
  • Compatibility and limits — capabilities and limits resolve as the minimum of the global and runtime values; a missing limit fails closed.
  • Authorization — a session-bound execution binding must authorize construction, and it is re-checked by the bridge at preflight.

Bedrock and legacy Java runtimes remain experimental: no runtime certification has been performed for them, so building is unavailable there by design.

  • Provider — Google Gemini adapter, your API key
  • Plan format — CraftMind BuildPlan v2
  • History — on-device, versioned, no account needed
  • Bridge — optional, private LAN, pinned identity
  • Certified target — Minecraft Java 1.20.1 · Fabric
  • Experimental — Bedrock · legacy Java 1.7.10 / 1.12.2
